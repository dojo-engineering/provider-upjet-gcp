# provider-upjet-gcp (Dojo fork)

Fork of [crossplane-contrib/provider-upjet-gcp](https://github.com/crossplane-contrib/provider-upjet-gcp)
carrying patches we need before they land upstream.

`main` mirrors upstream and is not used. We ship from **release branches**:
`release-<upstream-tag>` = that upstream tag plus our patches. Upstream's own
README is kept at [README.upstream.md](README.upstream.md).

(`main` is covered by an org ruleset requiring Wiz status checks, so it cannot
be force-pushed. `release-*` branches are unrestricted and match the build
system's default `RELEASE_BRANCH_FILTER`.)

**Exit condition:** when the upstream PR merges and a release containing it is
published, point clusters back at `xpkg.upbound.io`, then archive this repo.
A fork with no exit condition becomes permanent.

## Why a fork at all

The provider is code-generated from the Terraform provider schema. Adding a
resource means adding ~20 lines of configuration and regenerating; there is no
way to add a resource without rebuilding the provider package. Hence the fork.

We build and publish **only the service packages we patch** (`cloudtasks`), not
the whole family. The patched package declares a dependency on the *official*
`provider-family-gcp`, so it drops into an existing installation next to the
other `provider-gcp-*` packages.

## Repository layout

Only these files differ from upstream for a typical patch:

```
config/<scope>/<service>/config.go   # resource configuration (references, required fields)
config/externalname.go               # external-name / import-ID behaviour
examples/<service>/<scope>/<ver>/    # example manifests, used by e2e
```

Everything under `apis/`, `internal/controller/`, `package/crds/` and
`config/generated.lst` is generated by `make generate` and must be committed.

## Publishing a package

Published artefacts come from **git tags**, never from a branch.

```bash
git tag v3.0.0-dojo.1        # <upstream base>-dojo.<revision>
git push origin release-v3.0.0
git push origin v3.0.0-dojo.1
```

The tag push triggers the *Publish provider packages to GAR* workflow, which
builds the listed subpackages and pushes them to Artifact Registry with the tag
name as the package version. It can also be run manually from the Actions tab.

**Always verify the push** — the upstream build system makes `publish` a silent
no-op under several conditions (see Gotchas), so a green tick is not proof:

```bash
gcloud artifacts docker images list \
  europe-west2-docker.pkg.dev/dojo-creator-platform-nonprod/docker/provider-gcp-cloudtasks \
  --include-tags
```

### Versioning

`v<upstream-base>-dojo.<n>`, e.g. `v3.0.0-dojo.1`.

- states plainly which upstream release it is based on
- rebuilds of the same base increment `<n>`
- a new upstream base restarts at `.1`

Do not use `v3.0.1-...`; that implies an upstream release we are not based on.

## Installing

```yaml
apiVersion: pkg.crossplane.io/v1
kind: Provider
metadata:
  name: provider-gcp-cloudtasks
spec:
  package: europe-west2-docker.pkg.dev/dojo-creator-platform-nonprod/docker/provider-gcp-cloudtasks:v3.0.0-dojo.1
  packagePullSecrets:
    - name: ar-pull-secret
```

Notes:

- The official `provider-gcp-cloudtasks` must be removed first — two packages
  cannot own the same CRDs.
- Crossplane's package manager authenticates to private registries using
  `packagePullSecrets` (or an `ImageConfig`) **only**. It does not use GKE
  Workload Identity or the metadata server for unpacking. The secret lives in
  Crossplane's own namespace.
- Pin the image tag. Never `latest`, never a branch name.

## Rebasing onto a new upstream release

```bash
git remote add upstream https://github.com/crossplane-contrib/provider-upjet-gcp.git
git fetch upstream --tags

git checkout -b release-v3.1.0 v3.1.0
git cherry-pick <our-commit>...          # one per patch
make generate                            # resolve generated-file conflicts by
                                         # taking the new base, then regenerating
make reviewable
```

Conflicts land almost exclusively in generated files. Do not hand-merge them:
take the new base's version (`git checkout --ours <file>`), finish the
cherry-pick, then run `make generate` and amend.

When a patch lands upstream, drop that cherry-pick. When no patches remain,
delete the fork.

## Local development

```bash
make submodules                # build/ is a git submodule; nothing works without it
make generate                  # regenerate APIs, controllers, CRDs
make reviewable                # generate + lint + unit tests; tree must be clean after
```

End-to-end against a real GCP project (spins up its own kind cluster, does not
touch your current context's cluster — but it does switch your kubectl context):

```bash
export UPTEST_CLOUD_CREDENTIALS="$(cat sa-key.json)"
export UPTEST_GCP_PROJECT=<project-id>
export UPTEST_DATASOURCE_PATH=/tmp/uptest-datasource.yaml   # key: value map for ${data.*} in examples
export UPTEST_EXAMPLE_LIST="examples/cloudtasks/cluster/v1beta1/queueiammember.yaml"
make e2e
make controlplane.down
```

## Contributing patches upstream

Every patch here should have an open upstream PR. Raise it from a personal or
org fork against `crossplane-contrib/provider-upjet-gcp`, then reference the PR
number in the table at the top of this file. Upstream requires DCO sign-off
(`git commit -s`) with an email verified on the GitHub account that pushes.

## Gotchas

Discovered the hard way; all of these fail *silently*.

- **`make publish` does nothing off `main`.** `RELEASE_BRANCH_FILTER` defaults
  to `main master release-%`; on any other ref, `publish.artifacts` is never
  defined and make exits 0 having pushed nothing.
- **Tag builds are detached HEAD.** `BRANCH_NAME` comes from
  `git rev-parse --abbrev-ref HEAD`, which is the literal string `HEAD` on a
  tag checkout and therefore matches no filter. CI passes both `BRANCH_NAME`
  and `RELEASE_BRANCH_FILTER` as `${GITHUB_REF_NAME}`. The workflow's last step
  verifies the image exists in GAR, because neither of these failures shows up
  in the build output.
- **`PLATFORMS=` is ignored on macOS.** The build appends `linux_$(TARGETARCH)`
  whenever the host is not Linux. Use `PLATFORM=linux_amd64` (singular) to pin
  the architecture.
- **`build/` is a git submodule.** Without `submodules: true` / `make
  submodules`, every target fails with "No rule to make target".
- **Service packages are produced by `publish`, not `build`.** `make build`
  alone yields a runtime image and no `.xpkg`.
- **`CONFIG_DEPENDENCY_REG_ORG`** must stay `xpkg.upbound.io/upbound`, otherwise
  the package depends on a forked `provider-family-gcp` we never publish.
- **fish shell:** `PATH=(go env GOPATH)/bin:$PATH` expands a list into multiple
  arguments. Use `fish_add_path`, or `string join ':' $PATH`.
